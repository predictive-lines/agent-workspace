### Bug found in `google-workspace-mcp` v2.3.6 (non-fatal)
- `accounts add <name> -c <path>` saves the OAuth token BEFORE writing the per-account `credentialsPath` into `accounts.json`.
- `saveTokenForAccount` calls `loadCredentials(name)` which falls through to the *global* `credentials.json` since the account isn't registered yet.
- Result: token file has the wrong `client_id`/`client_secret` serialized in it.
- **Harmless at runtime** because `loadTokenForAccount` reconstructs the `OAuth2Client` with the correct per-account credentials and only uses `setCredentials()` for the refresh_token — client_id/secret in the token file are dead fields.
- Fixed cosmetically by rewriting `~/.google-mcp/tokens/oneoaks-personal.json` to have the correct `client_id`/`client_secret` (personal client). `accounts test-permissions` confirms auth works against the correct project.
- File an upstream issue if we ever feel like it; not blocking.

### Why `http://localhost:3000/?code=...` navigation looked "blocked"
- The `browser` tool's navigation-policy layer blocks reporting localhost HTTP as a navigation result, BUT Chromium already issued the GET before the block kicked in.
- The MCP callback server received the code and completed auth. Verified by polling the background process.
- Conclusion: ignore "browser navigation blocked by policy" errors on localhost OAuth callbacks — they're false-negative noise, the actual HTTP request went through.
